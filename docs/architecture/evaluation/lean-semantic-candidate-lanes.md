# Lean Semantic Candidate Lanes

Date: 2026-05-21

This document records the Prompt 69 semantic-lane repair. The change lets stable Lean-owned semantic facts propose
candidates before ranking and probing, through the candidate-source boundary added in Prompt 68.

## Design Note

Lean semantic extraction owns opaque statement fingerprints and role-feature keys. Search owns lane policy,
candidate-source merge, top-k selection, ranking input, and source-stage facts. Eval owns label joins and denominators.
Report owns projection and wording.

The smallest public interface is still a candidate-source fact attached to an observed declaration pair. Semantic lanes
add only stable `source_id`, `source_family = lean-semantic`, generation rank, saturation, and leak-safe feature-family
labels. Callers do not receive raw expressions, proof scripts, worker rows, retrieval keys, cache layout, private paths,
or vector facts.

The preserved user-facing capability is conservative symbolic cleanup: semantic-lane candidates may enter ranking, but
proof-neighborhood-style evidence cannot by itself make a default actionable finding. The Python-era behavior discarded
is treating Lean semantic work as only a late verifier for syntactically selected candidates.

## Design It Twice

Three designs were considered.

1. Broaden syntactic retrieval and hope probes rescue matches. Rejected because the problem is candidate discovery, and
   late probes cannot certify pairs that never enter the candidate queue.
2. Embed theorem statements or proof text and route through vector search. Rejected because this is the symbolic core
   path; embedding/model/backend facts remain in the hidden vector extension.
3. Add Lean-owned semantic lane facts as candidate sources behind the Prompt 68 boundary. Chosen because Lean owns the
   opaque facts, search owns merging and ranking, and eval can measure semantic-lane-only, symbolic-only, and merged
   recall without learning feature encodings.

## Implemented Lanes

The current worker/index surface truthfully supports two lanes.

| Lane id | Source family | Facts used | Release meaning |
| --- | --- | --- | --- |
| `lean-semantic.statement-meaning.v1` | `lean-semantic` | statement, safe-binder-permutation, connective, and conclusion fingerprints | Lean-owned statement-shape evidence selected through its own bounded lane top-k |
| `lean-semantic.binder-role-shape.v1` | `lean-semantic` | Lean role-feature keys such as conclusion and hypothesis constants/heads | Lean-owned binder/role evidence selected through its own bounded lane top-k |

Each lane has an independent per-anchor top-k. This means a candidate dropped by the mixed symbolic top-k can still be
merged into the ranked candidate set if a semantic lane selects it. Search records both source facts when a pair is
selected by both sources.

## Unsupported Lanes

Two planned lanes are intentionally not implemented yet.

| Lane | Current status |
| --- | --- |
| reducible definition summary | The worker exposes a summary string for display/comparison contexts, but there is no stable indexed equality key with a lane policy. |
| bounded proof-neighborhood summary | Probe and proof-grade evidence exists after candidate planning; the worker does not expose a stable pre-ranking proof-neighborhood key. |

These are blocked rather than faked from source text, declaration names, raw expressions, or proof scripts.

## Eval Denominators

Eval now reports `candidate_source_recall`:

| Field | What it counts |
| --- | --- |
| `symbolic_only` | labeled positives generated by `symbolic` source facts and not by `lean-semantic` source facts |
| `semantic_lane_only` | labeled positives generated by `lean-semantic` source facts and not by `symbolic` source facts |
| `merged` | labeled positives present after all candidate-source facts are merged |

Existing source-family and source-id candidate counts remain deduplicated unordered-pair counts. The default and
hard-negative gates still rely on visible hard-negative survival, not on lane availability alone.

## Verification Notes

The focused search test constructs a candidate that is outside the mixed symbolic top-k but inside the binder-role lane
top-k. The observed pair is `merged_generated` with a `lean-semantic.binder-role-shape.v1` source fact and no symbolic
source fact. This proves the lane is a real candidate source, not a relabeling of already selected symbolic candidates.

## Red Flag Review

- Shallow module: the lane workflow performs independent top-k selection and merge accounting; it is not a wrapper over
  existing selected candidates.
- Pass-through wrapper: eval receives source facts and denominators, not worker rows or retrieval keys.
- Temporal decomposition: the split follows hidden knowledge ownership: Lean facts, search merge policy, eval truth,
  report projection.
- Information leakage: raw expressions, proof scripts, source snippets, worker rows, private paths, cache layout, and
  vector facts stay out of public artifacts.
- Special-general mixture: only lanes supported by current stable facts are implemented; unsupported lanes are blocked
  explicitly.
- Conjoined methods: lane generation, ranking, label scoring, and report rendering stay separately owned.
- Hard-to-describe public API: a semantic lane is one candidate source family with stable lane ids and source facts.
- Implementation-detail comments: public comments describe lane facts and invariants, not fingerprint encodings or
  worker traversal mechanics.
